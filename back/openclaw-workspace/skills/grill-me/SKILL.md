# grill-me — Before You Code, Get Grilled

## 原则

在你动手写任何代码之前，先对需求进行「拷问式」审查。目标是：**在写下第一行代码之前，把方案想透、把坑踩完。**

触发方式：用户说「做XX」「写XX」「建XX」但需求不清晰时，自动执行。

## 拷问流程

### Phase 1: 基础定位

逐个抛出以下问题，根据用户的回答决定是否需要追问：

1. **这是什么？** — 一句话描述你要构建的东西
2. **为谁做的？** — 目标用户/使用场景
3. **最核心要解决的问题是什么？** — 存在的理由，不做会怎样
4. **现有的方案/替代品？** — 用户现在怎么解决的
5. **成功标准？** — 怎么知道做完了+做好了

**追问规则：** 用户回答每模糊一点，就追问「具体是指？」；如果用户给了具体答案，标记锁定进入下一题。

### Phase 2: 范围与边界

1. **MVP vs 完整版？** — 第一期做什么、什么可以以后做
2. **不做的是什么？** — 明确排除的scope
3. **依赖什么外部系统？** — API、数据库、第三方服务
4. **数据从哪来？** — 数据结构、数据量级

### Phase 3: 架构与技术

1. **运行环境？** — Browser/Node/Serverless/Mobile
2. **技术栈偏好？** — 框架、语言、数据库
3. **性能要求？** — 响应时间、并发量、数据量
4. **安全性要求？** — 认证、权限、数据隐私
5. **部署方式？** — 频率、方式、回滚策略

### Phase 4: 风险审查

1. **最大的不确定性？** — 什么可能搞砸
2. **假设了什么？** — 哪些前提如果错了就全盘皆输
3. **有没有类似方案踩过坑？** — 已知的坑
4. **回滚/挽回方案？** — 上线后出问题怎么办

## 输出格式

拷问结束后，输出一份结构化文档：

```
## 需求审查结论

### 一句话描述
{经双方确认的一句话定位}

### 核心需求（优先级排序）
1. P0: 必须有的功能
2. P1: 应该有但可以晚点
3. P2: 锦上添花

### 明确不做的
- 排除内容

### 技术方案（待确认）
- 运行时：
- 技术栈：
- 数据方案：

### 已知风险
- 风险1 + 缓解方案

### 下一步行动
- [ ] 确认上述方案
- [ ] 开始开发
```

## 行为规则

1. **一次只问一个问题。** 不要批量抛问题，等用户回答后再抛出下一个
2. **如果用户说「你先做你判断」** → 给出你基于已有信息的判断，并标注「如果方向错了请说停」
3. **如果用户说「不需要这么复杂」** → 快速收敛到最少问题：Phase 1 四问 + 风险一问你最担心的那个
4. **什么时候停止？** 当用户表现出不耐烦，或者你觉得风险已经足够低可以动手时
5. **用户已经给出了完整需求文档** → 跳过拷问，直接输出审查结论+标注发现的盲区
6. **不确定就问，不猜** — 宁可多问一句，不要事后返工
